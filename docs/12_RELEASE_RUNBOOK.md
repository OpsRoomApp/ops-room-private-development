# OPS ROOM v0.25.0 — Public Release Runbook

> The complete step-by-step for shipping **v0.25.0** (the installer bridge /
> Phase 1 release). Follow top to bottom. Every artifact and URL below is
> versioned for 0.25.0; the release pipeline is built so a later version only
> changes the numbers.

**Companion docs:** `docs/05_BUILD_DESTRUCTIVE_CLEANUP_AND_DEPLOYMENT.md`
(build pipeline internals), `../opsroom-website/DEPLOYMENT_UMAMI.md` (Umami).

---

## 0. What is v0.25.0 (installer bridge, #78 Phase 1)

- The updater understands **both** paths: zip (loose-folder installs, no
  elevation) and installer (Inno Setup, Program Files + registry).
- The manifest carries optional `installer_url` + `installer_sha256`; old
  updaters ignore them, the bridge updater uses them for installer-managed
  installs.
- **Phase 2 (v0.25.01 "switch to installed version" nudge) and Phase 3
  (installer-only, `download_url` = .exe) are NOT implemented.** This release
  is Phase 1: dual-publish zip + installer.

## 2. Build (Windows dev machine)

### 2a. Clean rebuild (if the build fails on a locked exe)

Symptom: PyInstaller aborts with
`PermissionError: [WinError 5] Access is denied: ...\dist\OPS ROOM\OPS ROOM.exe`
while removing the old dist folder. The running app locks the built exe, so
Windows cannot delete it.

```powershell
# 1. Close every running OPS ROOM instance (this is the lock)
Get-Process | Where-Object { $_.Path -like '*OPS ROOM*' } |
  Where-Object { $_.Path -like '*dist*' } | Stop-Process -Force

# 2. Clear the build caches (all regenerated by the build)
Remove-Item -Recurse -Force "$env:LOCALAPPDATA\Temp\OR250"   # venv + PyInstaller workpath + camera bridge build
Remove-Item -Recurse -Force "dist\OPS ROOM"                   # previous portable build
```

Then re-run `BUILD OPS ROOM COMPLETE.bat`. Nothing else needs clearing
(PyInstaller already runs with `--clean --noconfirm`).

Run **`BUILD OPS ROOM COMPLETE.bat`** from `opsroom-app/source/`. It:

1. Injects managed API keys (Lido, OpenAIP).
2. Builds the Camera Bridge 2024 (MSVC).
3. PyInstaller → `dist/OPS ROOM/`.
4. Runs `tools/validate_v0256_public_release.py` (77 checks).
5. Compresses `dist/OPS_ROOM_v0_25_0_Public_Windows_x64.zip` + `.sha256`.
6. Runs `tools/write_update_manifest.py --version 0.25.0 --site https://opsroom.live
   --installer ...` → `dist/update.json` with **website download URLs
   (`opsroom.live/downloads/...`) as primary** and **GitHub release copies as
   fallback** (`fallback_download_url` / `fallback_installer_url`).
7. Compiles `dist_installer/OPS_ROOM_Setup_0.25.0.exe` via Inno Setup 7.

**Expected artifacts:**

| Artifact | Path |
|---|---|
| Portable app | `dist/OPS ROOM/` |
| Release ZIP | `dist/OPS_ROOM_v0_25_0_Public_Windows_x64.zip` |
| ZIP checksum | `dist/OPS_ROOM_v0_25_0_Public_Windows_x64.zip.sha256` |
| Installer | `dist_installer/OPS_ROOM_Setup_0.25.0.exe` |
| Build manifest | `dist/update.json` (with installer fields) |

**Release notes:** copy the v0.25.0 section of `RELEASE_NOTES.md` into the
GitHub release body and the admin upload notes field.

## 3. Publish to GitHub (`OpsRoomApp/ops-room-releases`)

1. Create a **tag** `0.25.0` (and a release with the same name) on the
   `ops-room-releases` repo.
2. Attach **three** files:
   - `OPS_ROOM_v0_25_0_Public_Windows_x64.zip`
   - `OPS_ROOM_v0_25_0_Public_Windows_x64.zip.sha256`
   - `OPS_ROOM_Setup_0.25.0.exe`
3. Update the repo's **`main` `update.json`** (the raw fallback manifest the
   app fetches from `raw.githubusercontent.com/.../main/update.json`) to the
   built `dist/update.json` content. **It must keep `installer_url` +
   `installer_sha256`** (safety rail #5 — the fallback must be able to serve
   installer-managed installs). The GitHub release **tag must be exactly
   `0.25.0` (no `v` prefix)** — the `fallback_download_url` /
   `fallback_installer_url` in the manifest are built from that plain version.
4. Verify:
   ```bash
   curl -fsS https://raw.githubusercontent.com/OpsRoomApp/ops-room-releases/main/update.json | python -m json.tool
   curl -fsSI https://github.com/OpsRoomApp/ops-room-releases/releases/download/0.25.0/OPS_ROOM_v0_25_0_Public_Windows_x64.zip | head -3
   ```

## 4. Deploy the website + manifest (VPS)

### 4a. Push the website repo

The website repo carries the uncommitted v0.25.0 work: admin-api installer
manifest support, Download page installer button, `public/update.json`,
nginx, docker-compose, Umami. Commit + push, then on the VPS:

```bash
cd /opt/opsroom
git pull
docker compose up -d --build
docker compose ps   # opsroom-website, admin-api, umami, umami-db healthy
```

### 4b. Stage the release files on the VPS

```bash
# from your machine — the releases dir serves /downloads/ and /api/update.json
scp dist/OPS_ROOM_v0_25_0_Public_Windows_x64.zip  user@VPS:/opt/opsroom-releases/
scp dist_installer/OPS_ROOM_Setup_0.25.0.exe      user@VPS:/opt/opsroom-releases/
```

### 4c. Publish through the admin panel

1. Open `https://admin.opsroom.live/releases` (or `/upload`).
2. **Upload** `OPS_ROOM_v0_25_0_Public_Windows_x64.zip` (filename pattern is
   enforced). Paste the v0.25.0 release notes. → staged as DRAFT.
3. **Publish** from the Dashboard. The admin-api validates the SHA256, writes
   `/opt/opsroom-releases/update.json`, and because
   `OPS_ROOM_Setup_0.25.0.exe` is present it auto-adds:
   - `installer_url` → `https://opsroom.live/downloads/OPS_ROOM_Setup_0.25.0.exe`
   - `installer_sha256` → computed on the fly
   - `fallback_installer_url` / `fallback_installer_sha256` → the GitHub
     release copy (same bytes, so the same checksum)
4. The live manifest then points at the **website** for downloads
   (`opsroom.live/downloads/...`) with **GitHub as fallback** — exactly the
   primary/fallback split the app updater expects. The updater downloads from
   the website first and falls back to the GitHub URLs automatically if the
   site is unreachable or serves a bad file.

## 6. Umami (if not already set up) — summary

Full detail: `../opsroom-website/DEPLOYMENT_UMAMI.md`.

1. Deploy the stack (4a above) — `umami` + `umami-db` containers come up with
   an empty database.
2. Create the admin account (dashboard is localhost-only, so SSH-tunnel or
   curl):
   ```bash
   curl -sS -X POST http://127.0.0.1:3000/api/auth/setup -H 'Content-Type: application/json' \
     -d '{"name":"Ops Room","username":"<you>","password":"<strong>"}'
   ```
3. Create the website and note the `websiteId`:
   ```bash
   TOKEN=$(curl -sS -X POST http://127.0.0.1:3000/api/auth/login -H 'Content-Type: application/json' \
     -d '{"username":"<you>","password":"<strong>"}' | python -c "import sys,json;print(json.load(sys.stdin)['token'])")
   curl -sS -X POST http://127.0.0.1:3000/api/websites -H "Authorization: Bearer $TOKEN" \
     -H 'Content-Type: application/json' -d '{"name":"opsroom.live","domain":"opsroom.live"}'
   ```
4. Fill `.env` on the VPS: `UMAMI_USERNAME`, `UMAMI_PASSWORD`,
   `UMAMI_WEBSITE_ID`, `VITE_UMAMI_WEBSITE_ID` (same id), `UMAMI_APP_SECRET`,
   `UMAMI_DB_PASSWORD` (generate with
   `python -c "import secrets; print(secrets.token_urlsafe(32))"`).
5. `docker compose up -d --build` (rebuild so the tracker id is baked into
   the website bundle).
6. Verify:
   ```bash
   curl -fsSI https://opsroom.live/umami.js | head -3        # 200
   curl -sS -o /dev/null -w "%{http_code}\n" -X POST https://opsroom.live/api/send   # 400, not 404
   cd admin-api && python tests/test_analytics_umami.py     # 10/10
   ```
   Then `https://admin.opsroom.live/analytics`.
