# OPS ROOM — NOTAM Closure Marker SimObjects (v0.25.65)

In-simulator runway/taxiway closure markers driven by the live NOTAM feed.

## What this is

When a NOTAM closes a runway or taxiway (RWY/TWY + `CLSD` / `CLOSED` / `U/S`),
OPS ROOM parses the closure (`app/closure_markers.py`), places markers at the
closed runway thresholds using the bundled navdata, and — when the Briefing →
NOTAMS **DEPLOY IN SIM** toggle is enabled — spawns SimObjects into the
simulator via SimConnect (`SimConnect_AICreateSimulatedObject`).

Seven SimObjects matching real-world closure marking (ICAO/FAA layout):

| Object title (`sim.cfg`)              | Used for                     | Asset script               |
| ------------------------------------- | ---------------------------- | -------------------------- |
| `ORS CLOSURE MARKER X RUNWAY`         | white vinyl X mat, 60x10 ft  | `blender/make_x_marker.py --variant runway`  |
| `ORS CLOSURE MARKER X TAXIWAY`        | yellow vinyl X mat, 30x4 ft  | `blender/make_x_marker.py --variant taxiway` |
| `ORS CLOSURE MARKER X LIGHTED`     | vertical LED X on ground stand| `blender/make_lighted_x_trailer.py`          |
| `ORS CLOSURE BARRIER LOW ORANGE`      | water-filled barrier (orange)| `blender/make_barrier.py --variant orange`    |
| `ORS CLOSURE BARRIER LOW WHITE`       | water-filled barrier (white) | `blender/make_barrier.py --variant white`     |
| `ORS TYPE III BARRICADE ORANGE`       | single barrier + red beacon  | `blender/make_type3_barricade.py --variant orange` |
| `ORS TYPE III BARRICADE WHITE`        | single barrier + red beacon  | `blender/make_type3_barricade.py --variant white`  |

Barriers are deployed **alternating orange/white/orange/white** across the
closed runway at every hold-short position; the two color variants are
separate SimObjects so the spawner can alternate them.

### Hold-short deployment (real-world layout)

For a closed runway the plan places:

1. a white **X mat at each threshold** (heading = runway heading), and
2. **orange/white barrier lines ACROSS the runway** at every taxiway entry
   (hold-short position) and at every crossing runway.

Taxiway geometry comes from the **local Little Navmap DB first**
(`%APPDATA%\ABarthel\little_navmap_db\little_navmap_msfs.sqlite` — fresh,
includes addon airports), falling back to the **built-in taxi bundle**
(`surface_taxi_bundle` in `opsroom_aviation.sqlite`, generated by
`tools/build_taxi_bundle.py`). Airports with neither source still get the
threshold X's. Every placement carries `geometry_source`
(`local-lnm` / `built-in-bundle` / `navdata-centerline`) so the UI can show
where each marker came from.

### Type III barricade (`make_type3_barricade.py`)
A SINGLE barrier (same family as BARRIER_LOW_ORANGE — no folding leg),
delivered as **ONE continuous mesh body**.
- Base rail 1.8 m x 0.10 m deep x 0.20 m tall lies flat on the ground (origin
  at bottom-center, flush on pavement) with 1 cm corner bevels, an interlock
  notch cut into each end (8 cm wide x 5 cm deep) and 2 cm mounting
  through-holes 15 cm in from each end — all boolean-differenced.
- Full-face diagonal reflective stripes: a tileable 45-degree stripe image
  (pre-rendered PNG, simple EQUAL-WIDTH rectangular bands ~10.6 cm each,
  alternating orange/white) sampled over BOTH long faces' UVs (back face
  UVs mirrored so the diagonal reads the same from either side) - a real
  exported texture, so MSFS shows the stripes (not a flat color). A
  Layer-Weight Fresnel gloss adds the retroreflective sheeting response.
- Red emissive dome beacon (6 cm base + 5 cm lens) kept as a separate child
  object (`BEACON`) for flash animation. Round 9: the beacon FLASHES a red
  siren double-flash via a ModelBehaviors `<EmissiveFactor>` code block in
  the model.xml (see "In-sim lighting" below) - the sim evaluates the RPN
  every frame and multiplies the lens's STATIC emissive (80 = the flash
  peak) by a 0/1 pulse, so the dome is genuinely dark between pulses.
- End state: exactly 2 mesh objects (`BARRICADE_BODY`, `BEACON`). Renders a
  3/4-angle PNG + saves the .blend next to the exports. LOD0 + `_LOD1`.
  Both LODs export the `BEACON` node under its BASE name (the exporter
  strips the `_LOD1` suffix) so the behavior component's `Node="BEACON"`
  resolves at every LOD - a mismatched name would leave the distant LOD
  with a dark dome.

### Lighted X sign (`make_lighted_x_trailer.py`)
A **VERTICAL X sign** (the marker you see face-on on approach to a closed
runway): galvanized tripod ground stand holds the X up, two 2.75 m hub-to-tip
tubular arms cross at 90 deg through a visible hub bracket in the XZ vertical
plane. Mast + legs + feet + base plate + hub + arms are ONE continuous joined
body (`X_SIGN_BODY`); the 44 socket+dome fixtures are separate objects so they
can animate. `MAT_LightedX_Glow` emissive amber lenses. A **dominant red
obstruction beacon** (`CENTER_BEACON`) sits ON TOP of the hub at the X
intersection (real lighted-X markers carry a red beacon at the hub). The
script writes `--fixtures out.json` (local XYZ per light + `center_beacon`).

**In-sim lighting (round 9) is ModelBehaviors `<EmissiveFactor>` code - NO
fx, NO `systems.cfg` `[LIGHTS]`, NO keyframes.**

Two earlier mechanisms were proven dead on static SimObjects in MSFS 2024:
- Round 7: lightdef.N + custom `.fx` effects (staggered `Emitter Delay`
  chase, siren double-flash, billboard sprites, `NearFade`/`MinProjSize`
  draw-distance tuning) rendered STEADY and died at ~50-60 ft - legacy .fx
  emitters are FROZEN on static SimObjects (Rate / Particle Lifetime /
  Emitter Delay ignored) and the fx sprite + lightdef EmMesh cull at short
  range.
- Round 8: `ASOBO_property_animation` material keyframes (44 per-LED chase
  + siren) - the user saw the domes frozen at frame 0 (beacons red, LEDs
  dark): the engine does NOT play material keyframe animation on Misc
  SimObjects.

The mechanism that DOES run live is the ModelBehaviors **code** system: the
sim evaluates RPN code every frame for SimObjects (the SDK's Windsock sample
- an animated non-aircraft SimObject - ships `<Behaviors>`, and Asobo's own
blink template multiplies a material's emissive by `(P:Absolute time,
seconds)` arithmetic). The package builder writes one `<Component
Node="LENS_n">`/`<EmissiveFactor>` block per lens into each model's
`.xml`; the code output (0 or 1) multiplies the material's STATIC emissive
(exported at the flash peak), so the dome IS the light: visible at LOD
distance, no fx culling, no sprite.

Round 9 light behavior (user-driven):
- **X LED chase (runway-end-light style):** 44 components, one per
  `LENS_0..43` node, each with a staggered RPN chase code. A 2 s triangle
  wave sweeps the lit band from all four arm tips into the hub and back
  out (per-LED phase from the fixture's arm fraction t = 0.20 hub .. 1.00
  tip), so adjacent domes flash in sequence - a smooth travelling wave.
- **Siren double-flash beacons:** the X hub beacon (`CENTER_BEACON`) and
  the T3 rail beacon (`BEACON`) run the same RPN: two 0.12 s pulses 0.12 s
  apart per 1.5 s cycle (`t 1.5 % 0.12 <` OR `t 1.5 % 0.24 > t 1.5 % 0.36
  < and`), dark the rest of the cycle.
- **Brightness:** the static emissive (flash peak) is exported at the
  user-approved values - amber LEDs 400, X centre red 300, T3 beacon 80.
  The code returns 0 between pulses so the domes are genuinely dark, never
  "always lit". `UpdateFrequencyPreset="Asobo_Default_NeverStop"` keeps the
  code evaluating at ALL distances (the default preset stops at 1% screen
  size - the old "lights cut off" behaviour). The 1.5x X-scale fix keeps
  the LENS origins glued to the arms.

## Building the package (one-time asset build)

> **MSFS 2024 COMPILE REQUIRES THE OFFICIAL ASOBO EXPORTER.** The in-sim
> Project Editor / fspackagetool silently rejects glTFs exported by the stock
> Khronos exporter ("Output path does not exist" for the LOD gltf/bin, build
> fails with `_EndTreatCommands` errors). Models MUST be exported through the
> official Asobo MSFS2024 addon (`io_scene_gltf2_msfs_2024`) running in
> **Blender 4.2 LTS** — the addon lives in the SDK at
> `C:\MSFS 2024 SDK\Tools\Blender\addons\` and must be copied into the
> Blender 4.2 user addons folder (`%APPDATA%\Blender Foundation\Blender\4.2\scripts\addons\`)
> once. The driver below does exactly this; the generator scripts' own
> `main()` (stock exporter + `msfs_native` repack) is NOT accepted by the
> 2024 PackageBuilder.

1. Install **Blender 4.2 LTS** (e.g. `E:\Blender 4.2`) and copy the SDK addon
   `io_scene_gltf2_msfs_2024` into its user addons folder.
2. Export every model through the official exporter (this re-runs the
   generator, applies MODEL_SCALE, triangulates, and writes LOD0+LOD1 in the
   Asobo format):
   ```bat
   "E:\Blender 4.2\blender.exe" --background --python export_msfs_official.py -- barricade-orange "...\feedback\official_pilot_models\BARRICADE_T3_ORANGE"
   "E:\Blender 4.2\blender.exe" --background --python export_msfs_official.py -- barricade-white  "...\feedback\official_pilot_models\BARRICADE_T3_WHITE"
   "E:\Blender 4.2\blender.exe" --background --python export_msfs_official.py -- x-lighted      "...\feedback\official_pilot_models\X_LIGHTED_TRAILER"
   "E:\Blender 4.2\blender.exe" --background --python export_msfs_official.py -- barrier-orange "...\feedback\official_pilot_models\BARRIER_LOW_ORANGE"
   "E:\Blender 4.2\blender.exe" --background --python export_msfs_official.py -- barrier-white  "...\feedback\official_pilot_models\BARRIER_LOW_WHITE"
   "E:\Blender 4.2\blender.exe" --background --python export_msfs_official.py -- x-runway      "...\feedback\official_pilot_models\X_MARKER_RUNWAY"
   "E:\Blender 4.2\blender.exe" --background --python export_msfs_official.py -- x-taxiway     "...\feedback\official_pilot_models\X_MARKER_TAXIWAY"
   ```
   Export the output dir to the SAME drive as `blender/` (the exporter writes
   relative texture URIs; a cross-drive output silently drops the textures).
   The official driver (not the generator `main()`) is the only path that
   produces files fspackagetool accepts.
3. Stage the official 2024 project (SimObjects/Misc layout, texture relink
   + sidecars; the flashing/chasing lights are `<EmissiveFactor>` behavior
   code generated into each light model's `.xml` - no .fx files, no
   systems.cfg lightdefs, no glTF keyframes):
   ```bat
   python package\build_official_pkg.py
   ```
4. Compile in-sim: Dev Mode -> Project Editor -> File -> Open Project ->
   `feedback\fspkg_stage\Project.xml` -> Build. (The Store install blocks the
   CLI fspackagetool; the in-sim Project Editor is the reliable route.) The
   compiled package lands in `feedback\fspkg_stage\Packages\closure-markers\`.
5. Install that compiled package into the MSFS 2024 Community folder by
   replacing `%LOCALAPPDATA%\Packages\Microsoft.Limitless_8wekyb3d8bbwe\LocalCache\Packages\Community\closure-markers`
   with a copy of `feedback\fspkg_stage\Packages\closure-markers` (this is
   what the assistant does after each in-sim build). Do NOT use
   `build_package.py --install` for the official 2024 pipeline - that legacy
   tool rebuilds from the old exporter path and would install a stale
   package without the round-9 behavior lights. (It remains available only
   for the MSFS 2020 legacy install: `%APPDATA%\Microsoft Flight Simulator\Packages\Community`.)
5. Start MSFS, confirm the seven titles appear (or via Simvar Watcher), then
   enable **DEPLOY IN SIM** in Briefing → NOTAMS.

## How the injection works

1. `parse_active_closures(notams)` — conservative: reuses
   `notam_translate.is_closure_notam`, so it can only ADD markers.
2. `plan_markers(markers)` — runway closures place threshold X's plus
   hold-short barrier lines across the runway at every taxiway entry and
   runway crossing (local LNM DB first, built-in taxi bundle fallback);
   taxiway closures place at the airport reference point
   (`placement=airport-centroid`, documented simplification).
3. `spawn_markers(placements, enabled)` — dedicated lazy SimConnect session,
   `SimConnect_AICreateSimulatedObject` (the SDK export; the python SimConnect
   lib binds it as `dll.AICreateSimulatedObject`), one request per marker,
   handle passed by value exactly like the native bridge. Fire-and-forget:
   MSFS acknowledges asynchronously, so in-sim visibility is the acceptance
   test. Object IDs are captured from the async assignment.
4. `remove_markers()` — `SimConnect_AIRemoveObject` for every captured object
   ID. Safe no-op when nothing was spawned.

## Package layout (built)

```
package/closure-markers/
├── manifest.json                 # content_type MISC (regenerated by build_package.py)
├── layout.json                   # path/size/FILETIME-date per file
└── SimObjects/
    └── Misc/
        ├── X_MARKER_RUNWAY/      # sim.cfg + model/model.cfg + gltf/bin
        ├── X_MARKER_TAXIWAY/
        ├── X_LIGHTED_TRAILER/    # (+ _LOD1, fixtures.json)
        ├── BARRIER_LOW_ORANGE/
        ├── BARRIER_LOW_WHITE/
        ├── BARRICADE_T3_ORANGE/  # (+ _LOD1)
        └── BARRICADE_T3_WHITE/   # (+ _LOD1)
```

Notes:

- **`Model/` is the Blender export source and is never deleted by the
  builder.** Rebuild is: blender exports (official driver) →
  `build_official_pkg.py` (stage) → Project Editor build →
  `build_package.py --install`.
- Each SimObject folder has its own `sim.cfg` with `[General]
  category = StaticObject` (the category the OPS ROOM Bridge and the FNX cone
  use for SimConnect-spawned static objects) and a `model/model.cfg` +
  glTF/bin. MSFS 2020 and 2024 both accept `model.cfg` + glTF.
- The spawner matches on the **exact** `title` strings in each `sim.cfg`. If
  you rename an object, update `SIMOBJECT_TITLE_*` in
  `app/closure_markers.py` AND the `OBJECTS` list in
  `package/build_package.py`.

## Verification checklist (in-sim)

1. Open **Briefing → NOTAMS** and enable **DEPLOY IN SIM**.
2. The status line shows `N PLACED` with the placement list (thresholds,
   taxiway hold-short entries, runway crossings).
3. With a simulator running and a runway-closure NOTAM in the briefing, confirm
   an X appears at each closed threshold and orange/white barrier lines sit
   across the runway at every entry.
4. `GET /api/simobjects/notam-closures` shows `spawn.ok == true`.
5. Toggle off or press **CLEAR ALL** → objects are removed via
   `SimConnect_AIRemoveObject`.
